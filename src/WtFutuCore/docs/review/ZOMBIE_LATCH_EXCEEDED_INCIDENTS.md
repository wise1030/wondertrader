## 三、根因（两条叠加）

### 根因 A：撤单 ack 超时阈值(1000ms)扛不住开盘洪峰 → 假 ZOMBIE 升级
- 09:02 开盘瞬间叠加 PENDING_DRAIN 排水（pending_sell=31>30），撤单请求暴增，CTP ack 延迟 >1s。
- UnifiedOrderTracker 1s ack 超时 ×3 重试全败即升级 ZOMBIE → 触发闩锁。
- 这是**阈值型误报**：交易所并未拒单，只是慢。09:03:59 ack 到达即证。

### 根因 B：闩锁计时器复用陈旧时间戳 → EXCEEDED 瞬时误触发（代码级缺口）
- 09:02:26 telemetry 明确 `oldest holding 0ms`（新闩锁），3 秒后 EXCEEDED 却报 `held 136000ms`（= 自 09:00:13 首波闩锁起算）。
- 结论：** latch 自愈时未重置计时原点，再触发时继承了旧 _latch_since**，导致：
  1. EXCEEDED 判定失真（瞬时超限）；
  2. re-probe storm 被提前叫停（"engine cancelAll not resent"）——即本可通过重试解除的闩锁被错误地放弃治疗。
- 与 10-19 下午"三合约 120s×3 re-probe 不愈→转永久停报"同款机制：10-19 是 latch 真的不愈，10-22 是计时失真导致连重试机会都被剥夺。

## 四、健壮性缺口结论（P1，待方案入档）

1. **【代码 bug·优先】latch 重触发须重置 _latch_since**：自愈/解除路径清状态时应同时清计时原点；EXCEEDED 的 held 应以"本次连续持有"计。影响：每次开盘脉冲后 2 分钟内再触发闩锁，EXCEEDED 必误触发（十天中 10-19、10-22 两例均落在开盘/午后开盘 2 分钟窗口内，非偶然）。
2. **【阈值调优】撤单 ack 超时 1000ms 在开盘洪峰下过紧**：建议分级（普通 1s / 开盘与排水窗口 3~5s 或指数退避），避免把"慢"误判为"死"。ZOMBIE 升级前的重试预算（x3/1s）在洪峰下约 3~4 秒即耗尽，过于激进。
3. **【设计确认·已知情接受】cache-miss 不伪造终态 + 等真终态解除闩锁**：若交易所终态永远不到（极端），闩锁将永久停报到会话结束（10-19 下午即此形态）。这是治理批"宁响不哑"的有意取舍，但应配套**会话级兜底**：闩锁持续 >N 分钟升级 ERROR 并触发运维告警（现在只有日志，无主动通知）。
4. **【观测】PENDING_DRAIN 与开盘脉冲的共振**：pending_sell 阈值 30 在开盘秒级成交潮中易触发排水撤单，与策略重挂单叠加放大撤单洪峰。阈值或排水速率可调（低优先）。
